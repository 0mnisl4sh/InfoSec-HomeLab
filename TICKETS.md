# Тикеты стенда InfoSec HomeLab

25 заданий в формате заявок, которые реально падают младшему инженеру ИБ.
Порядок A → F логичный, но жёстко следовать ему не обязательно.

**Как работать.** На каждый тикет заводи отчёт `reports/LAB-XX.md` по шаблону
[reports/_TEMPLATE.md](reports/_TEMPLATE.md): что сделал, какими командами, чем проверил,
что пошло не так. Полчаса работы плюс
десять строк отчёта — и через месяц у тебя портфолио, которое на собеседовании
работает лучше любого списка технологий в резюме. Подсказки в тикетах намеренно
не содержат готовых команд целиком: гуглить и читать `man` — это и есть навык.

Легенда заголовка: `время · навыки`.

**Действующие лица.** `a.sokolov` — новый разработчик (его будешь заводить и потом увольнять).
`i.petrov` — «призрак»: учётка от уволившегося сотрудника, уже лежит в MySQL с прошлого года.

## Блок A. Доступы и Linux

### LAB-01 · Онбординг разработчика
**40 мин · Linux, доступы, MySQL, GitLab, RabbitMQ**

**Заявка от тимлида.** «С понедельника выходит Соколов Артём (`a.sokolov`), бэкенд.
Нужен доступ на app-01, чтение боевой базы, репозиторий и очередь. Сделай до пятницы.»

**Сделать.**
1. На `app-01`: пользователь `a.sokolov`, группа `developers`, вход только по SSH-ключу.
2. `sudo` строго на одну команду: перезапуск nginx. Ничего больше.
3. MySQL: доступ на чтение схемы `shop`, только из внутренней подсети.
4. Gitea: репозиторий `backend`, пользователь с правами на запись (не админ).
5. RabbitMQ: vhost `/app`, пользователь может читать из очередей, но не создавать и не удалять их.

**Приёмка.**
- Вход по ключу работает, вход по паролю для этого пользователя — нет.
- `sudo -l` показывает ровно одну разрешённую команду; `sudo cat /etc/shadow` отказ.
- `SELECT` в `shop` проходит, `INSERT` — ошибка прав; подключение с хоста вне подсети отбивается.
- `rabbitmqctl list_permissions -p /app` показывает ограниченные regexp'ы, а не `.*  .*  .*`.

**Подсказки.** `useradd -m -s`, `ssh-keygen -t ed25519`, файл в `/etc/sudoers.d/` +
обязательная проверка `visudo -cf`, `GRANT ... ON shop.*`, `rabbitmqctl set_permissions`.

### LAB-06 · Компрометация SSH-ключа
**45 мин · Linux, расследование**

**Заявка.** «Разработчик выложил приватный ключ в публичный репозиторий. Что делаем?»

**Сделать.**
1. Найти на сервере все файлы `authorized_keys` — у всех пользователей, включая root.
2. Для каждого ключа определить отпечаток и владельца.
3. Проверить по логам, были ли входы с этим ключом и когда.

**Приёмка.** Ты можешь показать: где лежал ключ, какой у него отпечаток,

и «точно не входил».

### LAB-07 · Брутфорс по SSH
**40 мин · Linux, логи, реагирование**

**Сделать.** Сгенерировать поток неуспешных входов и научиться его находить.

```bash
# с хоста: 30 попыток от несуществующих пользователей
for i in $(seq 1 30); do
  ssh -p 2222 -o BatchMode=yes -o StrictHostKeyChecking=no \
      -o ConnectTimeout=3 "user$i@localhost" true 2>/dev/null
done
```

Затем в `app-01` собрать из `/var/log/auth.log`: сколько попыток, с каких IP,
какие логины перебирали, попал ли кто-нибудь внутрь.

**Приёмка.** Однострочник, который выдаёт топ IP по числу неудачных попыток,
и ответ на вопрос «была ли хоть одна успешная авторизация с этого IP».

**Подсказки.** `grep`, `awk`, `sort | uniq -c | sort -rn`. Обрати внимание на разницу
формулировок `Invalid user`, `Failed password` и `Accepted publickey` — это разные события.

### LAB-11 · Отзыв сертификата и CRL
**30 мин · PKI**

**Сделать.** Отозвать выпущенный сертификат с причиной `keyCompromise`,
пересобрать CRL, проверить сертификат с учётом списка отзыва.
Посмотреть, как изменилась строка в `index.txt`.

**Приёмка.** `openssl verify -crl_check` падает с `certificate revoked`.
Ты можешь объяснить разницу между CRL и OCSP и почему от онлайн-проверки OCSP отходят:
Chrome давно не делает её сам (использует свои списки CRLSets), а Let's Encrypt в 2025 году
перешёл с OCSP на CRL. Причины — приватность (CA видит, какие сайты ты посещаешь),
задержки и то, что при недоступности OCSP-сервера браузеры всё равно пропускают соединение.
